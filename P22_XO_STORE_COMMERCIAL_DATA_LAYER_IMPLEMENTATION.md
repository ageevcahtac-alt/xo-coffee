## 3. Final Product Model

Таблица `public.products`, единственная новая сущность:

```sql
create table public.products (
  id                  uuid primary key default gen_random_uuid(),
  slug                text not null unique,
  name                text not null,
  description         text,
  price               integer not null check (price >= 0),
  published           boolean not null default false,
  passport_public_id  text,               -- см. раздел 4
  created_at          timestamptz not null default now(),
  updated_at          timestamptz not null default now()
);
```

Почему не больше и не меньше базового набора из задания:

| Поле-кандидат | Решение | Обоснование |
|---|---|---|
| `image`/`gallery` | **Не добавлено** | Не существует нигде в текущем продукте — ни в данных, ни в UI. Добавление было бы изобретением требования. |
| `weight`/вариант фасовки | **Не добавлено** | `packaging` сегодня — константа формы зерна, не вес; вариантов на лот нет вообще. Модель ниже (раздел 7) не блокирует появление весов позже, но не создаёт для них колонку без данных. |
| `stock`/inventory | **Не добавлено** | Не запрошено сценарием P22 (раздел 4 задания прямо говорит держать P22 только commercial foundation, inventory — "если потребуется", доказательств потребности сегодня нет). |
| `sort_order` | **Не добавлено** | Текущий порядок каталога — порядок массива в JSON плюс группировка по `category`; нет отдельного явного поля сортировки, которое стоило бы переносить. |
| `roast description`/`tasting copy` (`cupNote`, `farmStory`, `flavorProfile`, `sensory`) | **Сознательно НЕ перенесено в `products`** | Это canonical/origin-данные лота — ровно то, что задание запрещает дублировать (`lot_name`, `lot_region`, `lot_process`...). Они остаются в `src/data/lots.json` как есть (см. раздел 7) и в будущем — источник истины для них Coffee Passport, не Store. |
| `name`/`description` | **Добавлено** | Явно запрошены в минимальном наборе (раздел 4 задания) и оправданы: Product должен уметь существовать (черновик) до и независимо от привязки к Canonical Lot — значит нужны собственные, Store-owned commercial name/description, а не заимствованные у лота. |
| `price` | **Добавлено, как `integer`, не `numeric`/`float`** | Деньги никогда не хранятся с плавающей точкой. Единицы — целые рубли (не копейки/центы): проверено, что `formatPrice` и все 8 текущих цен никогда не используют дробную часть; вводить "копеечную" точность без единого подтверждённого кейса было бы преждевременным усложнением. |
| `published` | **Добавлено, `default false`** | См. раздел 6 — жизненный цикл черновика. |

## 4. Passport Reference Model

Поле: **`passport_public_id text`**.

Решение по имени подтверждено заново (не просто скопировано из P21): альтернативы `lot_id`/`lotId` отклонены, потому что эти имена в этом же репозитории уже означают Store-локальный slug (`CartItem.id`, `OrderPayloadItem.lotId`, `TastingRecord.lotId`) — переиспользование создало бы именно ту путаницу, которую задание требует развести. Префикс `passport_` явно маркирует поле как внешнюю, непрозрачную ссылку, а не Store-own identity.

Свойства:
- `text`, без парсинга формата (Coffee Passport сам решает форму `public_id`, Store её не валидирует и не интерпретирует);
- **не** foreign key — физического FK в другую базу быть не может (разные системы/базы); ссылочная целостность — забота будущего read-only integration-слоя (P23), не Postgres;
- **nullable** — см. раздел 6;
- **не unique** — см. раздел 7 (сознательное решение, не забытая деталь).

## 5. Why This Is Not a Canonical Lot

Прямое сравнение с тем, что задание запрещает создавать:

| Запрещено (раздел 2 задания) | Есть ли в `products`? |
|---|---|
| `lots`, `canonical_lots`, `green_lots`, `roast_batches`, `lot_owners` | Нет ни одной такой таблицы |
| `organizations → coffees → lots` как основа | Нет `organizations`, нет `coffees`, нет ownership-модели |
| Копия canonical-полей (`lot_name`, `lot_region`, `lot_process`, `lot_q_grade`, `lot_roaster`, ...) | Нет ни одного из них — единственная связь с canonical-данными — непрозрачный `passport_public_id` |
| Foreign keys, моделирующие roaster-ownership | Нет — `products` не знает, кто ростер, кто владелец лота, RLS не построен вокруг organization membership |

`products` не хранит происхождение, обжарку, вкусовой профиль, владение — только: как называется товар на витрине, сколько стоит, виден ли он, и (опционально) какой Canonical Lot он представляет. Это ровно граница "Store owns Product, Passport owns Canonical Lot" из раздела 1 задания, проверяемая построчно по схеме, а не только декларируемая в комментариях.

## 6. Product Lifecycle

Основание — фактический анализ, а не заданный в задании пример принят как есть без проверки.

Проверено: сегодня в живом коде **не существует** ни "черновика" продукта, ни состояния "опубликован/не опубликован" — каждый элемент `lots.json` уже полностью на витрине с первого дня (нет DB, нет CMS, весь файл = продакшн). Поэтому lifecycle, описанный в задании (draft → merchant выбирает Lot → publish), — это не то, что уже работает и просто переносится, а новое поведение, которое становится возможным только после появления этой таблицы.

Принятая модель:

```
1. draft:     passport_public_id = NULL,  published = false
2. linked:    passport_public_id = 'LOT-XO-...', published = false  (ещё не решили выставлять)
3. live:      passport_public_id = 'LOT-XO-...', published = true
```

**Осознанно не добавлен** `CHECK (published = false OR passport_public_id IS NOT NULL)`. Причина: сегодняшний каталог не даёт доказательства, что Store навсегда останется только про кофе с обязательной привязкой к Coffee Passport (мерч, подарочные сертификаты, будущие некофейные товары — ничего из этого не исключено архитектурой, просто не существует сегодня). Жёсткий constraint на уровне БД зафиксировал бы бизнес-правило, которое никто явно не подтвердил. Вместо этого это — **рекомендуемая конвенция для будущего merchant UI** (P24/P25), не ограничение схемы. Если владелец продукта подтвердит правило "нельзя опубликовать без Lot", constraint можно добавить отдельной миграцией в любой момент — так безопаснее, чем удалять поспешно введённое ограничение.

## 7. Current 8 SKU Migration Strategy

Данные **не переносятся в БД в этой сессии** — нет живой БД, к которой можно было бы что-либо применить (см. раздел 2). План перехода зафиксирован, но не выполнен:

```
src/data/lots.json (сегодня, живой источник storefront)
        │
        │  (будущий, отдельный шаг — не P22)
        ▼
одноразовый backfill-скрипт:
    products.slug               = lot.id            (сохраняет "lot-014" и т.п. — не рвёт
                                                       существующие cart/order/passport ссылки)
    products.name                = lot.name
    products.description         = <решение владельца — TBD, не lot.cupNote/farmStory,
                                     это canonical-поля, не commercial>
    products.price                = lot.price
    products.published            = true             (уже живой каталог)
    products.passport_public_id   = NULL              (P17 подтвердил: живого Passport-лота
                                                       с этими SKU сопоставить не с чем)
        │
        ▼
storefront ПРОДОЛЖАЕТ читать lots.json как сейчас,
пока не появится отдельное, осознанное решение переключить чтение на БД
(временный compatibility layer, если понадобится — не спроектирован в P22,
это отдельный будущий шаг, гипотеза из задания не принята как факт)
```

**В этой сессии `lots.json` не удалялся, не менялся, storefront не переключался на БД.** Big-bang миграция данных явно отклонена: раздел 15 задания прямо просит не делать её без необходимости, а необходимости (живой БД, живого Passport для сопоставления) сегодня физически нет.

Что нужно решить владельцу продукта до реального запуска backfill'а (не техническая проблема — продуктовая): чем именно должно стать `products.description` — коротким маркетинговым тизером, отдельным от `cupNote`, или просто пустым до появления настоящей коммерческой копирайт-политики. P22 не решает это за него.

## 8. Order Compatibility

Сегодня заказ вообще не персистится (только Telegram-уведомление) — `products` не связан ни с каким order-слоем, потому что order-слоя не существует. Это не откладывается специально — строить его прямо запрещено разделом 9 задания.

Зафиксирован только принцип для будущего (не спроектирован в деталях, не реализован):

- будущая `order_items` должна ссылаться на **`products.id`** (Store identity), не на текущий `lotId`/slug напрямую — `lotId`/slug остаётся адресуемым через `products.slug`, если понадобится обратная совместимость со старыми localStorage-заказами;
- если заказу нужно знать, какой именно Canonical Lot был куплен (для будущей аналитики/провенанса), правильный путь — **снимок (`snapshot`) значения `passport_public_id` на момент покупки** в самой строке заказа, а не живой join к `products` (Product/лот могут измениться или быть сняты с продажи после того, как заказ уже случился — историческая запись не должна "плыть" вслед за текущим состоянием каталога);
- **текущий Store `lotId` (`lot-014`-стиль) никогда не должен интерпретироваться как Canonical Lot identity** ни в каком будущем order-объекте — ровно предупреждение раздела 9 задания, зафиксировано явно, чтобы не повторить ошибку `coffeePassportLink.ts` (см. P21 §7.2) на новом слое.

## 9. RLS / Security

Приняты минимальные, объяснимые в один шаг правила — без придумывания ролей, которых не существует:

```sql
alter table public.products enable row level security;

create policy "products_select_published"
  on public.products for select
  using (published = true);

-- insert/update/delete: сознательно НЕ созданы никакие политики.
```

Обоснование:
- **Read (published-only)** — это ровно то, что нужно сегодняшнему витринному сценарию (анонимный посетитель видит опубликованный каталог) и ничего больше — черновики (`published = false`) не видны никому через анонимный/authenticated ключ.
- **Write — запрещено всем клиентским ролям.** В репозитории нет ни одного файла auth/admin/merchant (подтверждено повторно в разделе 1) — придумывать роль "merchant" сейчас означало бы гадать про схему, которую P20/P21/P22 явно откладывают на P24/P25. Единственный способ писать в эту таблицу сегодня — service-role ключ из доверенного server-only контекста (никогда не браузер), используемый вне RLS, вручную/скриптом — то есть ровно так, как раздел 12 задания и просит: "минимальная безопасная базовая модель", без сложной системы ролей.
- Никакой Coffee Passport credential, никакой service-role ключ нигде в клиентском коде не добавлялся — не было причины: интеграция с Passport в P22 не подключается вовсе.

## 13. Known Limitations

- `products` не связан ни с чем в runtime — это чистый задел, не действующая таблица. Пока не появится решение переключить хотя бы часть storefront на БД, эта миграция будет "просто лежать", как и старая P14-миграция лежала до этого момента — тот же риск (раздел 1 P21-отчёта, п.1) применим и к ней, если её тоже забудут при следующей фазе.
- `products.description` содержимое для реального backfill'а 8 текущих SKU не определено — продуктовое решение владельца, не техническое (раздел 7).
- Нет constraint'а, гарантирующего "нет published без passport_public_id" — сознательно (раздел 6), но это значит, что до появления merchant UI с собственной валидацией ничто на уровне БД не мешает вручную (service-role) опубликовать Product без привязки к Lot. Это допустимо на данном этапе, но должно быть учтено при проектировании merchant UI (P24/P25).
- RLS сегодня в принципе не может быть протестирован против реальных ролей — нет ни одного пользователя, ни одной сессии, потому что нет auth. Политика `products_select_published` проверена только чтением SQL, не live-запросом.

## 14. Exact P23 Plan

**P23 — XO Store ↔ Coffee Passport Read-Only Integration Boundary**

Должен спроектировать (не реализовать) поверхность, через которую XO Store сможет получить:

> активные Canonical Lots, принадлежащие XO COFFEE Roasting (`roaster.slug = "roaster-xo"`, per P20).

Конкретика, которую P23 обязан зафиксировать:
1. Форма контракта: что именно возвращает интеграционная поверхность на один Lot (минимум — `public_id`, вероятно `name`/`country`/`region` для отображения в будущем merchant picker'е, точный набор — предмет самого P23, не P22);
2. Где физически живёт клиент этой поверхности в Store — расширение уже предложенного в P21 `src/lib/passport/server.ts` (server-only, по образцу `src/lib/supabase/server.ts`), не браузерный код;
3. Как фильтр по ростеру (`roaster-xo`) применяется — на стороне Passport (предпочтительно, раз RLS/логика владения уже там) или как параметр запроса от Store — решение P23, не P22;
4. Явное подтверждение, что это НЕ прямой Supabase-клиент к публичным таблицам Passport (P21 §12 — "публичная строка" ≠ "безопасно для произвольного внешнего клиента"), а отдельная, контролируемая read-only поверхность;
5. Как результат этой поверхности будет маппиться на `products.passport_public_id` в будущем merchant picker UI (сам picker — не в P23, только контракт данных, которые ему понадобятся).

P23 **не подключает** реальный Passport API, не создаёт merchant picker, не пишет код синхронизации — только проектирует контракт, аналогично тому, как P22 спроектировал и создал только схему `products`, не подключая её к рантайму.
