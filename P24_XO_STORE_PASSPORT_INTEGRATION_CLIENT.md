## 1. Executive Summary

## 2. P23 Contract Consumed

Контракт принят **как описан в задании**, без возможности сверить с фактическим исходником P23 (см. оговорку в разделе 0):

```
public_id   — string, обязательное
name        — string, обязательное
country     — string | null
region      — string | null
variety     — string | null
process     — string | null
q_grade     — number | null
```

**Не расширялся** — ни `internal uuid`, ни `roaster uuid`, ни любые дополнительные поля не добавлялись, ровно по прямому запрету раздела 8 задания.

**Nullability полей `country`/`region`/`variety`/`process`/`q_grade`** — это единственное место, где пришлось делать обоснованное предположение, а не читать факт. Основание: в этом же репозитории уже лежит (deprecated, никогда не применённая) P14-миграция `20260911120000_coffee_passport_foundation.sql`, где `public.coffees.country`/`region` и `public.green_lots.variety`/`process`/`q_score` — все без `NOT NULL`. Contract из задания называет поле `q_grade`, а не `q_score` из той миграции — это тоже не унифицировано мной, оставлено как есть, потому что это внешний, не Store-контролируемый контракт, а не опечатка, которую стоит "исправлять". **Это предположение о nullability не подтверждено против реального P23-кода** — если фактический контракт помечает эти поля как обязательные (`not null`), валидатор (раздел 6) нужно будет соответственно ужесточить отдельным изменением, не в этой сессии.

`public_id` и `name` — единственные поля, трактуемые как строго обязательные строки, потому что без них ни идентификация, ни отображение лота невозможны в принципе — это не предположение, а логическая необходимость самого контракта.

## 3. Store Environment Configuration

Проверена существующая конвенция перед добавлением новых переменных (раздел 4/6 задания — "изучи текущий `.env.example`... не копируй имена вслепую"):

| Существующий паттерн | Что он показал |
|---|---|
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | server-only секреты называются без префикса, только по назначению — не `XO_STORE_TELEGRAM_TOKEN` |
| `NEXT_PUBLIC_COFFEE_PASSPORT_LOT_URL_TEMPLATE` | уже существующий прецедент: всё, что относится к внешнему Coffee Passport, называется с префиксом `COFFEE_PASSPORT_*` |
| `render.yaml` | все секреты — `sync: false`, задаются вручную в Render-панели, не хранятся в репозитории |

**Добавлены две новые переменные**, следуя обоим найденным паттернам:

```
COFFEE_PASSPORT_INTEGRATION_URL       — server-only, НЕ NEXT_PUBLIC_*
COFFEE_PASSPORT_INTEGRATION_SECRET    — server-only, НЕ NEXT_PUBLIC_*
```

- `COFFEE_PASSPORT_INTEGRATION_URL` хранит **полный URL** конкретного P23-эндпоинта (`.../api/integrations/xo-store/lots`), не "базовый origin" — раздел 6 задания прямо просит не создавать несколько URL-конфигураций, а сегодня потребляется ровно один эндпоинт.
- `COFFEE_PASSPORT_INTEGRATION_SECRET` — это Store-сторонняя копия того же значения, что Coffee Passport хранит под именем `XO_STORE_INTEGRATION_SECRET` (раздел 4 задания). Имя переменной **намеренно другое** — не скопировано вслепую: каждый репозиторий называет свои env-переменные исходя из собственной точки зрения (см. `TELEGRAM_BOT_TOKEN` — Store не называет его "MY_OWN_MESSAGING_TOKEN"), значение при этом должно совпадать между двумя системами.

Изменены три файла: `.env.example` (документация + пустые плейсхолдеры, публично закоммиченный файл), `.env` (пустые плейсхолдеры для локальной разработки — файл в `.gitignore`, не попадёт в коммит), `render.yaml` (два новых `sync: false` env var — значения задаются вручную в Render, не в репозитории).

## 5. Authentication

Используется ровно то, что задание описывает для P23: `Authorization: Bearer <secret>`. Не изобретён никакой другой механизм (не query string, не custom header, не cookie).

```ts
headers: { Authorization: `Bearer ${secret}` }
```

Secret никогда не появляется:
- в URL/query string — подтверждено чтением кода: `fetch(url, {...})`, `url` не модифицируется добавлением параметров;
- в client-side коде — модуль не импортирован ни одним `"use client"` файлом (раздел 4), а сама переменная окружения не имеет префикса `NEXT_PUBLIC_*`, значит Next.js её вообще не инлайнит в клиентский бандл (см. раздел 10, проверено сборкой).

## 6. Runtime Validation

Проверено перед выбором подхода: в `package.json` нет ни `zod`, ни `yup`, ни любой другой validation-библиотеки (те же зависимости, что были в P17/P21/P22 — не изменились). Раздел 9 задания прямо разрешает использовать существующий подход, если он есть — и он есть: `src/lib/coffeePassport.ts` уже реализует ровно такой паттерн вручную (`isValidOrderRecord`, `isValidTastingRecord` — проверка типа поля за полем, отказ от значения целиком при первом несовпадении). Новый валидатор `isValidLot()` в `coffeePassportClient.ts` написан в том же стиле — не введена тяжёлая validation-библиотека без необходимости, ровно как просил раздел 9.

Проверяется:
- `response.status` (401/403 обрабатываются отдельно от общего "не ok" случая — раздел 11);
- что тело — валидный JSON (`try { await response.json() } catch`);
- что верхний уровень — массив (`Array.isArray`);
- что **каждый** элемент массива проходит `isValidLot` — обязательные `public_id`/`name` как непустые строки, остальные поля — `string | null` / `number | null` (раздел 2). Один невалидный элемент отклоняет весь ответ целиком, а не отфильтровывает его молча — сознательный выбор: тихая потеря одного лота была бы хуже явной ошибки интеграции.

## 7. Error Handling

Пять категорий, ровно по разделу 11 задания:

| Категория | Триггер | Возвращаемое значение |
|---|---|---|
| Configuration error | `COFFEE_PASSPORT_INTEGRATION_URL`/`_SECRET` не заданы | `{ kind: "not_configured" }` — **fetch не вызывается вообще** (подтверждено тестом) |
| Authentication failure | P23 → `401` | `{ kind: "unauthorized" }` |
| Forbidden | P23 → `403` | `{ kind: "forbidden" }` |
| Passport unavailable | сетевая ошибка/timeout (`catch` вокруг `fetch`) или любой другой не-2xx статус | `{ kind: "unavailable" }` (сеть) / `{ kind: "unavailable", status }` (HTTP-статус, известен) |
| Invalid contract | JSON не парсится, не массив, или элемент не проходит `isValidLot` | `{ kind: "invalid_contract", detail }` |

Функция **никогда не бросает исключение** — каждый `catch` превращён в типизированный `{ ok: false, error }`, так что ни один вызывающий код не может случайно "утечь" наружу stack trace, secret, внутренний URL или Supabase/сетевые детали (буквально то, что раздел 11 запрещает показывать пользователю) — потому что сырое исключение просто никогда не долетает до вызывающей стороны в первую очередь.

## 8. Timeout / Cache

**Timeout:** `AbortSignal.timeout(8_000)` — 8 секунд на один запрос. Выбрано без стороннего пакета: `AbortSignal.timeout` — часть платформы, доступна в Node ≥20 (проект уже требует `>=20.9.0` в `package.json.engines`), поэтому не требует новой зависимости. Никакого retry — один controlled request, ровно как просит раздел 12 задания.

**Cache:** сознательно **не реализован**. Обоснование: сегодня эту функцию не вызывает ни один route/компонент (раздел 4) — кэшировать нечего, добавление кэша сейчас было бы преждевременной оптимизацией без единого реального вызова для измерения. Более того, раздел 13 задания прямо предупреждает: "не делай долгий cache, который может скрывать новые Lots" — при нулевом текущем трафике риск от отсутствия кэша равен нулю, а риск от неудачно подобранного TTL — не равен нулю. Решение отложено до появления реального вызывающего кода (P25+), когда будет с чем сверять реальную частоту вызовов.

## 9. Product Compatibility

Требование раздела 14 задания: доказать, что `public_id` из P23-ответа типово совместим с `products.passport_public_id`, не автоматически создавая записи.

- `products.passport_public_id` (P22-миграция) — `text`, nullable, без ограничения формата.
- `CoffeePassportLot.public_id` (этот отчёт) — `string`, непустая.

Совместимость — по построению, без адаптера: `string` из TypeScript один в один ложится в Postgres `text` без преобразования формата, потому что ни одна сторона не навязывает свою схему значения (ни regex, ни длина, ни префикс не проверяются ни там, ни там — оба места сознательно остаются "непрозрачными" к содержимому, см. P21 §10/P22 §4). Никакого кода, который бы фактически писал в `products`, в P24 не создано — ни одной строки `INSERT`/`UPDATE` нигде в новом коде, подтверждено чтением `coffeePassportClient.ts` целиком (раздел 4) — файл не импортирует ничего из `src/lib/supabase/`.

## 13. Live Verification

**Не выполнялась.** Причина — не техническое ограничение, а честная невозможность: в этой среде нет ни реального значения `COFFEE_PASSPORT_INTEGRATION_URL` (адрес развёрнутого P23), ни реального `COFFEE_PASSPORT_INTEGRATION_SECRET`. Что проверено вместо этого — вся цепочка логики **против замоканного P23** (раздел 11): корректный ответ, 401, 403, 5xx, сетевой сбой, невалидный JSON, невалидная форма — все 11 сценариев проходят с ожидаемым типизированным результатом.

**Что нужно, чтобы включить настоящую live-проверку** (не выполняется в этой сессии): владельцу — вписать реальные `COFFEE_PASSPORT_INTEGRATION_URL`/`_SECRET` в `.env` (локально) или в Render dashboard (продакшн), после чего `fetchXoRoasterLots()` можно вызвать из временного server-side контекста (например, консолью Next.js dev-сервера через `next/dist/...` REPL или разовым server action) для однократной ручной проверки — не как постоянный debug-эндпоинт (раздел 17 задания это прямо запрещает), а как одноразовое действие владельца вне этой сессии.

**P25 — Merchant Lot Picker / Product Creation Flow**

Должен впервые дать магазину действие "выбрать Canonical Lot → выставить его как Product на витрине", используя `fetchXoRoasterLots()` из P24 как единственный источник списка лотов. Конкретика, которую P25 обязан зафиксировать (не реализуется в P24):

1. **Auth-предпосылка.** P25 не может быть построен без хотя бы минимального merchant/admin аутентификационного контура — в репозитории сегодня 0 auth-файлов (подтверждено повторно в этом отчёте, раздел 1 P21). Это должно быть либо частью P25, либо отдельным явным предшествующим шагом — решение владельца, не техническая деталь.
2. **UI-поверхность.** Экран со списком результатов `fetchXoRoasterLots()` (public_id/name/country/region/variety/process/q_grade — ровно тот контракт, что уже типизирован в P24), с действием на каждой строке "создать Product с этим `passport_public_id`" или "привязать к существующему Product".
3. **Запись в `products`.** Использует `passport_public_id`-колонку из P22 напрямую — P24 уже доказал типовую совместимость (раздел 9), P25 должен реализовать сам `INSERT`/`UPDATE` через service-role/серверный контекст (не через анонимный ключ, RLS из P22 не даёт клиентских write-политик).
4. **Никакого автоматического импорта.** Раздел 22 задания и здравый смысл интеграции: P25 — это merchant-инициированное, по одному лоту за раз, действие, не batch-синхронизация.
5. **Диагностика несоответствия.** Раздел 16 задания предлагает сравнение "Available Passport Lots" со статическим каталогом — в P25 это может стать частью самого merchant UI (показать, какие Passport-лоты ещё не представлены ни одним Product), не отдельным скриптом.

P25 не реализуется в этой сессии — только формулируется, ровно как этот же принцип применялся к формулировке P24 в конце P23-этапа.
