## 4. Найденные accessibility-проблемы

### 4.1 Контраст: `--color-gold-dark` не проходит AA нигде, где используется (ГЛАВНАЯ находка)

Токен `--color-gold-dark` (`#a9872c`) используется **исключительно** как `text-gold-dark` — построчная проверка (`grep -rn "gold-dark" ... | grep -v "text-gold-dark"` → 0 совпадений) подтвердила: ни разу как фон, ни разу как бордер, ни разу в тёмных секциях (Header/Footer/Manifest используют для акцента обычный `gold`, не `gold-dark`). Это единственный "restrained accent"-цвет для десятков eyebrow-лейблов и заголовков секций по всему сайту ("Каталог", "Подход", "Ноты в чашке", "Технические данные" и т.д.) — как правило, `text-xs`/12px, что не подпадает под исключение "крупный текст" (нужно 18pt/24px обычным начертанием или 14pt/18.66px полужирным).

Расчёт (WCAG relative luminance): **3.20:1 на cream, 2.96:1 на cream-dark** — оба ниже требуемых 4.5:1 для обычного текста.

### 4.2 Контраст: десятки подписей на `text-charcoal/40–60` и `text-burgundy/40–60`

Системная (не единично-случайная) проблема — везде, где непрозрачность текста подбиралась "на глаз" под ~40–60%, реальный контраст оказывается ниже порога:

| Непрозрачность | Контраст на cream/surface |
|---|---|
| `/40` | 2.39–2.47:1 |
| `/45` | 2.73–2.83:1 |
| `/50` | 3.13–3.27:1 |
| `/55` | 3.61–3.79:1 |
| `/60` | 4.18–4.42:1 (оба ниже 4.5!) |
| `/65` | **4.88–5.19:1** ← минимальная безопасная непрозрачность |

Затронуто 11 файлов (полный список — раздел 6), в основном подписи метаданных, региона/сорта/обработки, спецификаций рецепта, итогов заказа, данных о доставке/оплате — то есть ровно то, что задание просило проверить особо ("region/process/variety... цены... error messages").

### 4.3 Контраст: `text-cream/40` на тёмном Footer

`Footer.tsx` — копирайт-строка и "Pure Roast" — 3.61:1 на `bg-surface-accent` (burgundy-dark), ниже 4.5:1.

### 4.4 Клавиатурная навигация: двойное срабатывание на карточке каталога (реальный баг, не только контраст)

`Catalog.tsx` — карточка лота: `<article role="button" tabIndex={0} onKeyDown={handleCardKeyDown}>`, внутри — реальная кнопка "В корзину" (`onClick={handleAddToCart}`, без своего `onKeyDown`). `keydown` всплывает от кнопки к родительской статье независимо от `click` — значит, клавиатурный пользователь, нажавший Enter/Space, находясь на кнопке "В корзину", **одновременно** добавляет лот в корзину И открывает модалку паспорта лота — двойное, конфликтующее действие, которого не происходит у пользователя мыши (`handleAddToCart` вызывает `event.stopPropagation()` только для `click`, не для `keydown`). Найдено построчным чтением кода событийной модели, не визуальным тестом — воспроизводимо детерминированно (стандартное поведение всплытия DOM-событий, не требует браузера для подтверждения).

### 4.5 Формы: 8 полей полагались только на `placeholder` как единственный label

`CheckoutForm.tsx` — поля Имя/Телефон/Email; `PaymentStep.tsx` — номер карты/срок/CVC/название компании/ИНН. Ни у одного не было ни видимого `<label>`, ни `aria-label` — только `placeholder`, который (а) исчезает при вводе текста, (б) не гарантированно даёт устойчивое "accessible name" для скринридера в реальном времени, (в) сам факт "placeholder как единственный label" прямо назван в задании как то, что нужно проверить. При этом **в том же файле уже существует правильный образец** — поле `address` уже использует `aria-label={ADDRESS_LABELS[carrier]}` рядом с `placeholder` — новые правки лишь распространяют уже принятый в проекте паттерн, не изобретают новый.

### 4.6 Формы: ошибка телефона не связана с полем программно

`CheckoutForm.tsx` — `{phoneError && <p>Введите номер полностью...</p>}` рендерился рядом с полем, но без `aria-describedby`/`aria-invalid` на самом `<input>` — скринридер, стоящий на поле, не узнает об ошибке автоматически.

### 4.7 Формы: `<select>` "Точка самовывоза" — видимый `<label>` без программной связи

`<label>` существовал, но без `htmlFor`, `<select>` — без `id`: визуально подпись есть, программно не связана.

### 4.8 ARIA: `role="radio"`/`aria-checked` на способе оплаты — неполный и вводящий в заблуждение паттерн

`PaymentStep.tsx` — три кнопки способа оплаты помечены `role="radio"`/`aria-checked`, но **без** обёртки `role="radiogroup"` и без реализации стрелочной навигации между вариантами (стандартное ожидание ARIA APG для радио-паттерна). Скринридер объявит "radio button", пользователь ожидаемо попробует стрелки — они не сработают. Это хуже, чем отсутствие ARIA вовсе (несовпадение объявленной роли и реального поведения) — прямое нарушение принципа задания "не создавать искусственную accessibility-разметку" в его негативной форме (используется не для галочки, а неверно).

### 4.9 Success-состояние — уже корректно (находка "не проблема", зафиксирована для полноты)

`OrderSuccess.tsx` уже передаёт "успех" не только цветом — есть иконка-галочка И заголовок "Заказ №X оформлен" текстом. Единственное, чего не хватало, — программного объявления скринридеру, что этот контент только что появился (это не toast, а замена содержимого drawer на новом шаге, без навигации страницы).

### 4.10 Модалки/Drawer — уже полностью корректны (находка "не проблема")

`useDialogFocus.ts`, `ui/Modal.tsx`, `ui/Drawer.tsx` — построчно проверены: `role="dialog"`, `aria-modal="true"`, осмысленный `aria-label` на каждом экземпляре, фокус переносится внутрь диалога при открытии, Tab/Shift+Tab корректно зациклены внутри (focus trap), Escape закрывает **только самый верхний** из стека открытых диалогов (учтён случай вложенных модалок — LotPassportModal поверх DiscoveryModal), фокус возвращается на триггер при закрытии. Уже полностью соответствует ожидаемому поведению — **не изменялось**.

## 5. Какие проблемы подтверждены расчётом

Все контрастные находки (4.1–4.3) подтверждены точным числовым расчётом по формуле WCAG relative luminance/contrast ratio через отдельный Node-скрипт (не входит в проект, только для верификации в этой сессии) — не оценкой "на глаз". Полная таблица контроль-точек — раздел 4.2. Клавиатурная находка (4.4) подтверждена анализом DOM event bubbling (детерминированное поведение браузера, не требует визуального теста). Находки по формам (4.5–4.7) и ARIA (4.8) подтверждены прямым чтением JSX/DOM-структуры — присутствие/отсутствие атрибутов проверяется точно, без домысливания.

## 6. Внесённые исправления

**Токен (1 значение, глобальный эффект):**
- `app/globals.css` — `--color-gold-dark: #a9872c` → `#7f6521` (та же тональность, темнее — 5.23:1 на cream, 4.84:1 на cream-dark). Безопасно ровно потому, что токен нигде не используется как фон/бордер и никогда — в тёмных секциях (см. 4.1) — исправление одной строки чинит все использования сайта разом, не создавая новый оттенок сверх уже существующего.

**Контраст текста (`/40`–`/60` → `/65`, `/55` для placeholder, `/50` для Footer's cream), 11 файлов:**
`Catalog.tsx`, `DiscoveryModal.tsx`, `FlavorProfileChart.tsx`, `Footer.tsx`, `LotPassportModal.tsx`, `cart/CartItemsView.tsx`, `cart/CheckoutForm.tsx`, `cart/OrderSuccess.tsx`, `cart/PaymentStep.tsx`, `passport/CoffeePassportDetail.tsx`, `passport/MyCoffeePage.tsx`, `ui/SegmentedControl.tsx`. Иконки-кнопки (prev/next/close с `aria-label`, без видимого текста) **не трогались** — для графических UI-элементов достаточно 3:1 (WCAG 1.4.11), а `/60` даёт 4.18:1, что уже проходит; изменение опустошало бы усилие впустую и не было предметом находки.

**Клавиатурная навигация:**
- `Catalog.tsx` — `handleCardKeyDown` теперь игнорирует событие, если `event.target !== event.currentTarget` (событие всплыло от вложенной кнопки, не сгенерировано самой карточкой) — единственное изменение логики в этой сессии, 5 строк с комментарием, объясняющим причину.

**Формы:**
- `CheckoutForm.tsx` — `aria-label` на полях Имя/Телефон/Email (мимикрируя уже существующий паттерн у `address`), `autoComplete="name"/"tel"/"email"`, `aria-invalid`/`aria-describedby`/`id="phone-error"` для ошибки телефона, `htmlFor`/`id` для связки `<label>`↔`<select>` "Точка самовывоза".
- `PaymentStep.tsx` — `aria-label` на номере карты/сроке/CVC/названии компании/ИНН, `autoComplete="cc-number"/"cc-exp"/"cc-csc"/"organization"`.

**ARIA:**
- `PaymentStep.tsx` — способ оплаты: `role="radio"`/`aria-checked` → `aria-pressed` (тот же корректно работающий toggle-button паттерн, что уже используется в `Catalog.tsx`/`DiscoveryModal.tsx` для похожих групп выбора — унификация, не изобретение).

**Semantic states:**
- `cart/OrderSuccess.tsx` — `role="status"` на корневой контейнер, чтобы переход к шагу "успех" внутри уже открытого drawer был объявлен скринридеру (контент подменяется без навигации страницы — нативных средств для этого нет).

## 7. Какие проблемы сознательно НЕ исправлены

- **Не введена** обёртка `role="radiogroup"` со стрелочной навигацией для способа оплаты — вместо починки неполного radio-паттерна выбрано **упрощение** до уже работающего в проекте `aria-pressed`-паттерна (см. 4.8) — то же решение, но по принципу "минимальное исправление", не "нарастить ARIA-инфраструктуру".
- **Не введён** `aria-current`/active-state индикатор для `Header`'s навигации — не регрессия, задокументированное с самого начала (`src/lib/nav.ts`) минималистичное решение; задание прямо просит не добавлять новые пункты/функциональность.
- **Не переведены** табы каталога (`aria-pressed`) на полноценный ARIA `tablist`/`tab`/`tabpanel` — текущий toggle-button паттерн валиден по ARIA APG как альтернатива табам без необходимости roving-tabindex; перевод на tablist добавил бы сложность, не устраняя подтверждённую проблему.
- **Не двигается программно фокус** на заголовок нового шага при переходе `cart → checkout → payment → success` внутри `CartDrawer` — решено ограничиться `role="status"` (раздел 6) как минимальным достаточным средством; принудительный перенос фокуса — более инвазивное поведенческое изменение, не запрошенное явно и не обязательное при уже работающем focus trap.
- Двойной `aria-label="Меню"` на `Drawer` и вложенном `<nav>` в `MobileMenu.tsx` — минорная избыточность объявления, не нарушение WCAG, оставлено как есть.
- Не создавался новый lint/audit-инструмент — использован уже существующий `eslint-plugin-jsx-a11y` (см. раздел 3).

## 16. Ограничения browser-проверки

Как и в P27/P28 — расширение Chrome не подключено в этой среде (`"Browser extension is not connected"`, идентичная ошибка, воспроизведена перед началом работы). Ни одна находка не подтверждалась визуально/скриншотом. Вместо этого:
- каждая контрастная находка подтверждена **точным числовым расчётом**, а не приближением;
- клавиатурная находка подтверждена анализом фактической событийной модели DOM (детерминированное поведение, не требующее рендера);
- находки по формам/ARIA подтверждены прямым чтением JSX-разметки (наличие/отсутствие атрибутов — бинарный факт, не требующий визуального теста).

Первый шаг любой будущей сессии с доступом к браузеру — реальная клавиатурная и screen-reader проверка (NVDA/VoiceOver) всех сценариев из этого отчёта, особенно исправление в `Catalog.tsx` (раздел 4.4) и новую радио→toggle-семантику в `PaymentStep.tsx` (раздел 4.8), которые логически корректны, но не проверялись живым ассистивным ПО.
