## 1. Executive Summary

Эта аудит-сессия проверяла, соответствует ли текущий репозиторий модели **Roaster → Café → Guest → Public Passport** и цепочке **Coffee → Green Lot → Canonical Lot → Roast Batch → Reference Roast Profile / Reference Taste Profile → Passport/Tasting/My Coffee**, описанной в задании P13.

Главный и определяющий результат аудита:

> **Ни ролевая модель (Roaster / Café / Guest / Public), ни многоступенчатая модель данных (Coffee → Green Lot → Canonical Lot → Roast Batch → Reference Roast/Taste Profile) не существуют в этом кодовой базе — ни частично, ни в зачаточном виде.** Это не «почти реализовано с недочётами» — это отсутствует полностью: нет аутентификации, нет ролей, нет базы данных, нет RLS, нет отдельных сущностей Green Lot / Canonical Lot / Roast Batch.

Фактически существующий продукт — это **единый (single-tenant) публичный D2C-сайт кофе-обжарщика** без аккаунтов, без бэкенда с базой данных, с одной плоской сущностью `Lot` (см. `src/types/lot.ts`) и с Coffee Passport, полностью реализованным на localStorage конкретного браузера.

В рамках того, что фактически существует, продукт внутренне согласован, детерминирован и уже прошёл углублённую верификацию в фазах P7–P12 (funnel, data integrity, mobile, content/brand, launch readiness). Новых P0-проблем в существующей системе не найдено. Два findings уровня P1 касаются не багов, а того, что вся запрошенная архитектура ролей/данных — это 100% новая работа, а не доработка существующего кода.

**Код не менялся.** Ниже — честная карта фактического состояния.

## 6. Architecture Findings

### Finding 1 — Ролевая модель Roaster/Café/Guest/Public полностью отсутствует

- **Severity:** P1
- **Location:** весь проект (отсутствие, а не конкретный файл) — подтверждено построчным grep по `src/`, `app/`; единственные совпадения на «role» — ARIA-атрибуты (`role="dialog"`, `role="button"` и т.п.), не относящиеся к продуктовым ролям.
- **Evidence:** нет auth-библиотек в `package.json`; нет `login`/`session`/`jwt` кода (единственные совпадения на «session» — комментарии про время жизни браузерной вкладки, не аутентифицированная сессия); нет маршрутов для входа или разграничения интерфейсов.
- **Why it matters:** принцип ownership («только Roaster владеет Canonical Lot») невозможно ни реализовать, ни нарушить — потому что нет субъектов (Roaster, Café), между которыми распределяются права. Если эта ролевая модель — реальное продуктовое направление, это полностью новая архитектурная работа (аутентификация, роли, БД, RLS), а не доработка существующего кода.
- **Recommended direction:** *(зафиксировано как gap, implementation plan вне рамок P13)* — перед реализацией нужно явно решить: нужна ли multi-tenant архитектура вообще для текущей бизнес-модели (единственный обжарщик-ритейлер) или же роли Roaster/Café относятся к будущему продуктовому направлению, которое ещё не запущено.

### Finding 2 — Модель данных Coffee → Green Lot → Canonical Lot → Roast Batch → Reference Profiles отсутствует

- **Severity:** P1
- **Location:** `src/types/lot.ts`, `src/data/lots.json`
- **Evidence:** единственная сущность — `Lot`, плоская структура с 16 полями (origin-данные, sensory-данные и `flavorProfile` — все на одном объекте, без разделения на «зелёный лот» и «конкретную обжарочную партию»). Данные приходят из одного статического JSON-файла, встроенного в билд — не из БД, не из multi-stage pipeline.
- **Why it matters:** сегодня невозможно смоделировать «один и тот же Green Lot обжарен в две разные Roast Batch с разным результатом в чашке» — `flavorProfile` жёстко привязан к `Lot`, а не к отдельной обжарочной партии. «Reference Roast Profile» и «Reference Taste Profile» как различающиеся сущности не существуют — есть один профиль на лот.
- **Recommended direction:** *(gap only, без implementation plan)* — если многопартийная модель обжарки нужна, придётся вводить отдельную сущность Roast Batch с собственным `flavorProfile`, независимую от Green/Canonical Lot record.

### Finding 3 — Принцип ownership «только Roaster редактирует Canonical Lot» соблюдается тривиально, а не по дизайну

- **Severity:** P3 (наблюдение, не нарушение)
- **Location:** `src/data/lots.ts` (`export const LOTS: Lot[] = lotsData as Lot[]`)
- **Evidence:** во всём runtime-коде нет ни одного пути мутации `LOTS` — ни для Café, ни для Guest, ни для самого «Roaster». Массив — константа, вычисленная на этапе импорта модуля.
- **Why it matters:** правило «Café не может создать shadow-копию Canonical Lot» сейчас выполняется — но не потому, что есть проверка прав, а потому, что мутировать данные лота не может вообще никто во время работы приложения. Это не то же самое, что «ownership enforced» — это «mutation surface отсутствует полностью». Если в будущем появится любой способ редактирования лота (хотя бы для Roaster), эту гарантию придётся строить с нуля, а не «включить существующий guard».
- **Recommended direction:** нет действия сейчас; зафиксировано для будущего, когда появится любая forма редактирования каталога.

### Finding 4 — UX и backend согласованы в том, что оба одинаково молчат о Roaster/Café-модели

- **Severity:** нет (positive finding, не проблема)
- Специально проверено по разделу 9 задания: UI (Approach-секция) описывает процесс обжарки как внутренний нарратив бренда («Зерно → Анализ → Профиль → Обжарка → Каппинг → Коррекция → Раскрытие»), но **не подаёт это как интерактивную функцию с разными ролями**. Ни в одном месте интерфейс не намекает на существование Café как отдельного актора, который получает Lot от Roaster. Значит, здесь нет расхождения «UI обещает одну модель, backend — другую»: обе стороны консистентно **не реализуют** multi-actor модель, а не конфликтуют друг с другом.

### Finding 5 — Редактируемость Coffee Passport проверена на предмет «immutable source» противоречия — противоречия не найдено

- **Severity:** нет (positive finding)
- В `CoffeePassportDetail.tsx` пользователь может нажать «Изменить» и пересохранить свою дегустацию (кнопка `Изменить` → `loadRecordIntoForm` → повторный `saveTastingRecord` с тем же `id`). Это могло бы выглядеть как нарушение «Passport показывает данные как immutable, но позволяет редактировать источник» — но фактически редактируется только **личная запись пользователя** (`MyCupRating` + заметка), а не референсные данные лота (`flavorProfile`, `qScore`, origin-поля), которые нигде в UI не редактируются. Разграничение «объективный профиль лота vs личное впечатление» проведено честно и последовательно (уже подтверждено в P7/P11) — здесь нет противоречия.

## 7. Security / RLS Findings

- **RLS-политик, anon key, service-role key разграничения — не существует, потому что не существует базы данных.** Раздел проверки «может ли Café/Guest технически получить/изменить то, что должен контролировать только Roaster» — неприменим буквально (нет Café, нет мутируемых данных), но по существу отвечает: **нет, никто не может ничего мутировать во время работы приложения**, включая гипотетического Roaster.
- Единственный секрет в проекте — `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`, используется исключительно в `app/api/order/route.ts` (server-only Route Handler), не импортируется ни в один `"use client"` компонент — проверено построчным grep, повторяет выводы P8/P9. **Не найдено новых утечек.**
- **Forward-looking finding (Severity: P2, не блокирует сегодняшнюю систему):** `src/lib/orderNumber.ts` генерирует `orderNumber` как `XO-${6 случайных цифр}` через `Math.random()`, без криптографической случайности и без проверки уникальности на сервере (проверка уникальности реализована только локально, при записи в `localStorage` — `saveOrderRecord` дедуплицирует по `orderNumber`, но это защита от дублей в ОДНОМ браузере, а не от коллизий между разными покупателями). Сегодня это не эксплуатируемая уязвимость, потому что `/passport/[orderNumber]` резолвит данные только из локального `localStorage` — у другого пользователя просто нет доступа к чужому `localStorage`, поэтому угадать чужой номер заказа физически не даёт доступа к чужим данным. **Но если когда-либо появится общий backend/БД, хранящий заказы централизованно, эта же схема идентификаторов (короткий, предсказуемый, неуникальный на сервере номер) превратится в IDOR-класс уязвимость** — любой сможет перебором 900 000 значений открывать чужие Coffee Passport. Рекомендация на будущее (не сейчас): при добавлении любой централизованной персистентности заменить схему `orderNumber` на криптографически случайный или UUID-based идентификатор с серверной проверкой уникальности, а не переносить текущую схему как есть.

## 8. Data Integrity Findings

- **FK/relationships:** неприменимо — данные не реляционные, единственная связь (`TastingRecord.lotId` → `Lot.id`) резолвится клиентским поиском (`LOTS.find(...)`), не foreign key constraint. Уже проверено на устойчивость к «сироте» (удалённый из каталога лот) в P7/P9 — обрабатывается честно, без крэша и без fake-плейсхолдера.
- **UUID vs public_id:** `Lot.id` — стабильные hand-assigned slug'и (`lot-014`, `espresso-nol`, `specialty-degustation`), не UUID. `orderNumber` — короткий человекочитаемый номер (см. Security-раздел выше про его слабые стороны). `TastingRecord.id` — `${lotId}-${crypto.randomUUID()}` при доступности `crypto.randomUUID`, иначе `${lotId}-${Date.now()}-${random}` fallback — уже проверено как приемлемо collision-resistant в P8.
- **localStorage как source of truth:** подтверждено буквально — `xo-coffee-cart`, `xo-coffee-orders`, `xo-coffee-tastings` — это единственное, откуда читаются Cart/Orders/Tastings, и это осознанное, задокументированное в UI решение («История дегустаций хранится локально, в этом браузере — без аккаунта и синхронизации между устройствами»), а не архитектурная случайность. Задание просило проверить «не используется ли localStorage как источник истины там, где источником должна быть Supabase/Postgres» — ответ: **да, localStorage — единственный источник истины везде, потому что никакой Supabase/Postgres не существует, чтобы быть альтернативой.** Это не нарушение существующей архитектуры (нечего нарушать), но это прямая причина, почему Finding 1 и Finding 2 (роли и многоступенчатая модель данных) сегодня физически не могут быть реализованы без предварительной миграции с localStorage на серверную БД — localStorage принципиально не может быть источником истины для системы с несколькими типами акторов (Café не увидит то, что «видит» чужой Guest-браузер; «Public» в смысле «видно с любого устройства» не может работать на клиентском хранилище).
- **Дублирование данных:** `CartItem` денормализует `name`/`price` лота на момент добавления в корзину (не хранит только `lotId` со ссылкой) — это уже было проверено как осознанное, полезное решение (P8: чек должен показывать цену на момент покупки, а не текущую цену лота), не проблема целостности.

## 9. Deferred / Non-blocking

- Полноценная имплементация Roaster/Café ролей — сознательно не в рамках этой фазы (аудит-only, задание явно просит не придумывать архитектуру и не писать implementation plan).
- Миграция orderNumber на криптографически безопасную схему — не нужна, пока нет централизованного backend; отложено до момента, когда появится реальная необходимость (см. Security Finding).
- Юридические страницы (оферта / политика ПДн / возврат) — уже зафиксированы как отдельный отложенный риск в P12, сознательно не дублируются здесь.

---

## 10. Final Verdict

# READY FOR IMPLEMENTATION

Аудит завершён честно: запрошенная архитектура Roaster/Café/Guest/Public и модель Coffee→Green Lot→Canonical Lot→Roast Batch **не существуют** в этом кодовой базе ни в каком виде. Это не «блокер» в смысле «что-то ломается» — в системе, которая **реально существует** (single-tenant D2C сайт с одной сущностью Lot и Coffee Passport на localStorage), P0-проблем не найдено, и её собственная внутренняя согласованность подтверждена данным аудитом и предыдущими фазами (P7–P12).

Вердикт `READY FOR IMPLEMENTATION`, а не `BLOCKED`, означает: карта текущего состояния получена, гэп чётко локализован (роли + многоступенчатая модель данных + миграция source-of-truth с localStorage), и теперь можно осознанно спланировать следующий implementation block — именно так, как и предполагает задание P13.
